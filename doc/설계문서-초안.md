## 1. 한 줄 정의

> **차 안에서, 지금 배터리와 목적지를 보고 — 내가 가진 멤버십 기준으로 가장 싸고 확실히 되는 충전소를 경로에 넣어주고, 아낀 돈과 효율 운전을 차가 직접 확인해 보상해 주는 Pleos 앱.** [결정]

서비스명: **VIA** — **V**erified rewards · **I**n-route · **A**ffordable ("~을 경유하여") · 팀명: **볼트앤페이(Volt&Pay)** [결정, 2026-10-25]

## 2. 왜 만드는가 (근거)

| 문제 | 근거 |
|---|---|
| **충전 요금 구조가 복잡해서 손해를 본다** | 같은 kWh가 270~590원, 비회원가는 회원가의 최대 2배, 완속 사업자 57.9%가 현장 요금 미표시 (한국소비자원 2025-12). 요금 구조 불만은 국내 126건 vs 해외 48건 — **한국 특유** |
| **요금 불만이 지금 가장 뜨겁다** | 충전 앱 부정 리뷰 중 요금 언급 2025년 12.0% → **2026년 21.4%** |
| **회원가를 받으려면 가입 장벽이 있다** | 평균 4~5개 멤버십 보유, 충전 앱 부정 리뷰의 18%가 로그인·가입 문제. "충전소에서 적용 가능한 멤버십이 표시되면 좋겠다"는 직접 요청 |
| **충전기 고장이 1순위 불편** | GS차지비 1,400명 조사 52.7% |
| **사람들은 '아껴주는 기능'과 리워드를 좋아한다** | 국내 충전 앱에서 요금 언급의 63%, 리워드 언급의 89%가 긍정. 리워드 언급률은 해외의 약 19배 |
| **운전 → 보상은 폰 앱으로는 실패했다** | 모두의충전 "캐시백 드라이빙": 수동 시작·종료, GPS 오류로 주행거리 0 기록 → 혜택 축소 → 사전 공지 없이 삭제 |
| **해외 보상 앱은 '차량 연결'에서 실패한다** | Optiwatt·ev.energy 리뷰의 20%가 차량 연결 문제, 87% 부정 ("연결 끊김으로 보상 누락", "피크 시간에 충전") |

→ **차 안의 Vehicle SDK로 배터리·주행·충전을 직접 읽는 앱**은 폰·클라우드 앱이 실패한 지점(연결·검증)을 구조적으로 피한다. 이것이 핵심 차별점이다.

## 3. 목표 · 비목표 · 반목표

### 목표
1. 공용 충전을 할 때 **내 멤버십 기준 실제 단가**로 경로상 충전소를 비교해 가장 싸고 쓸 수 있는 곳을 추천한다.
2. 추천한 충전소를 **내비 경유지로 바로 넣는다.**
3. 아낀 금액을 **원 단위**로 보여준다.
4. 효율 운전·비피크 충전·이벤트 충전소 이용을 **차량 센서로 자동 검증**해 포인트를 준다.
5. **충전소 스탬프 투어 + 레이드형 이벤트 충전소**로 다시 오게 만들고, 동시에 충전 수요를 분산시킨다. [결정]

### 비목표 (이번에 안 함)
- 결제 기능 자체 구현 — 결제는 **카페이 연동을 전제**로 기획서에 쓰고, 시연은 결제 확인 화면까지만
- 통행료 합산 비용 최적화 (근거 없음, H3) [결정]
- 충전 대기 중 즐기는 게임 (근거 없음, H4) [결정]
- 전비 저하 원인 설명(XAI) (근거 약함, H5) [결정]
- AR (SDK에 카메라·AR 없음, 게임 분류 위험) [결정]
- 집(아파트) 완속 충전 요금 최적화 — 사업자를 고를 수 없어 효과가 작음. 요금 표시·비교 정도만

### 반목표 (기능은 돌아가도 이러면 실패)
- **주행 중 화면 조작을 요구한다** → 심사 탈락 + 위험
- **앱이 "게임"으로 분류된다** → 주행 중 실행 자체가 막혀 핵심 기능까지 못 씀
- **느리다** (국내 통합 앱 반발의 1순위 원인: 공감 4,366·2,705·1,567)
- **특정 충전사업자 편을 든다** → 통합·중립 앱만 사랑받는다는 데이터와 반대
- **리워드를 나중에 줄이거나 사용을 막는다** → 반발이 가장 큰 지점
- **추천대로 갔는데 충전기가 고장** → 신뢰가 한 번에 무너짐

## 4. 사용자와 핵심 장면

### 주 사용자 [결정]
**공용 충전을 쓰는 EV 운전자** — 집 충전기가 없거나, 출장·장거리·외부 일정이 잦은 사람.

### 핵심 장면 (데모·PT 시나리오와 같음)

**장면 A — "배터리가 부족한데 어디서 충전하지?" (주행 중)**
1. 운전자가 내비에 목적지를 입력하고 출발한다.
2. 앱이 배터리 잔량·전비·경로 거리로 **도착 시 잔량**을 계산한다. 기준(예: 15%) 아래면 충전이 필요하다고 판단한다.
3. 경로 위 충전소 중 **고장·사용 중이 아니고, 내 멤버십 기준 가장 싸고, 우회가 적은 곳**을 고른다.
4. **음성 안내만**: "도착 시 배터리가 8%예요. 12km 앞 ○○충전소에 들르면 내 멤버십 기준 kWh당 120원 더 저렴해요. 경유지로 추가할까요?"
5. 운전자가 음성으로 "응" (STT) → 경유지 추가. 화면 터치는 필요 없다.

**장면 B — 충전 시작 (정차)**
1. 충전소에 도착해 충전을 시작하면 앱이 충전 상태 변화를 감지한다.
2. 정차 화면에 표시: 적용 요금(내 멤버십), 비회원가 대비 **예상 절약액(원)**, 이번 방문으로 얻을 **스탬프·포인트**.
3. 이 충전소가 처음이면 "새 스탬프!" (도감에 추가).

**장면 C — 레이드형 이벤트 충전소 (사전 알림)**
1. "오늘 22시~02시, ○○충전소 포인트 2배" — 정차 중 홈 화면 카드 또는 출발 전 음성 1회.
2. 그 시간에 그곳에서 충전하면 **위치 + 시간 + 충전 상태**로 자동 검증 → 포인트 2배.
3. (사업 관점) 한산한 시간·장소로 수요를 옮기는 대가를 충전사업자·가맹점이 낸다.

**장면 D — 주간 리포트 (정차)**
이번 주 절약액(원), 효율 운전 연속 기록, 새 스탬프, 같은 차종 리그 순위, 포인트로 받을 수 있는 할인 쿠폰.

### 5-2. 추천 로직 (F2~F4)

**도착 시 잔량** — 스파이크에서 내비가 주는 "도착 시 배터리값"은 신뢰할 수 없다고 확인됐다(Battery Energy 기준, 소모 미반영). **앱이 직접 계산한다.** [결정 — 스파이크 근거]

```
남은 에너지(kWh) = SoC(%) × 배터리 용량(kWh)
경로 소모(kWh)   = 남은 거리(km) ÷ 전비(km/kWh)     ← 전비는 EvBattery의 현재/누적 전비
도착 시 SoC      = (남은 에너지 − 경로 소모) ÷ 배터리 용량
충전 필요        = 도착 시 SoC < 기준값 [제안: 15%]
```

- **배터리 용량**: Vehicle SDK에 용량 API가 없다. **VIN → 차종 → 용량** 대응표로 구한다 [제안]. 표에 없으면 온보딩에서 차종을 고르게 한다.
- 전비가 아직 없으면(출발 직후) 차종 기본 전비를 쓴다.

**충전소 순위** — 후보 = 경로에서 일정 거리 이내 + 도착 전에 닿을 수 있는 충전소.

```
필요 충전량(kWh) = (목표 SoC [제안: 80%] − 그 충전소 도착 시 SoC) × 용량
실효 단가        = min(내가 가진 멤버십 각각의 단가, 로밍가, 비회원가)
총비용(원)       = 필요 충전량 × 실효 단가 + 우회 비용
우회 비용        = 우회 거리 × 전비 환산 비용 + 우회 시간 × 시간 가치 [제안: 시간 가치는 0으로 시작, 설정에서 조정]
제외             = 고장·점검·사용 불가 / 내 차 커넥터 불일치 / 도착 시 SoC가 안전 하한 미만
```

- 동점이면 **충전 속도(kW)가 빠른 곳**을 우선한다 [제안].
- 추천은 **1곳만 음성으로**, 나머지 2곳은 정차 시 화면에서 비교 [제안].

### 5-3. 리워드 규칙 (F7, F9)

**원칙** [결정 — 리뷰 근거]
- 사용자가 아무것도 누르지 않아도 **차량 데이터로 자동 검증**된다.
- **현금처럼 쓰는 포인트가 아니다** → 제휴 충전 할인 쿠폰으로만 교환 (선불전자지급수단 규제 회피).
- **한 번 공지한 적립 기준은 시즌 중 줄이지 않는다.** 바꿀 땐 다음 시즌부터, 미리 알린다.
- 유효기간은 짧게 하지 않는다 [제안: 12개월].

**적립 항목** [제안 — 수치는 모두 조정 가능]

| 항목 | 검증 데이터 | 기준 (예시) |
|---|---|---|
| 효율 운전 | EvBattery 전비, Odometer 트립 거리 | 트립 전비가 **같은 차종 기준 전비** 이상, 트립 10km 이상 |
| 비피크 충전 | 충전 상태 변화 + 시각 | 지정 시간대(예: 23~07시) 충전 시작 |
| 이벤트(레이드) 충전소 | 위치(지오펜스) + 시각 + 충전 상태 | 이벤트 시간·장소에서 충전 → 배수 적용 |
| 새 충전소 스탬프 | 위치 + 충전 상태 | 처음 충전한 충전소 |

- 주행거리 자체에는 보상하지 않는다 (공회전·불필요 주행 유도 방지). **효율에만** 보상한다.
- 같은 충전소 스탬프는 1회. 이벤트 배수는 하루 1회.

### 5-4. 게이미피케이션 (F8~F10) [결정]

- 포켓몬 고의 **"스폰서 장소" 구조**를 가져온다: 게임이 사람을 특정 장소·시간으로 보내고, 그 장소가 대가를 낸다 (맥도날드 재팬 3,000곳, 스타벅스 미국 7,800곳 선례).
- **모든 게임 화면은 정차 중에만** 열린다. 주행 중에는 음성 한 줄만 ("새 스탬프 획득!").
- 앱 분류는 **충전 유틸리티**. 게임 요소는 그 안의 기능이다.
- 구성 요소: 충전소 스탬프 도감 → 레이드형 이벤트 충전소 → 효율 운전 연속 기록 → (이후) 차종별 주간 리그.
- 캐릭터·애니메이션은 이번 범위에서 뺀다 [제안 — 일정].

## 6. 화면과 상태

### 6-1. 차량 상태별 동작 [결정 — Pleos 심사 기준]

| 상태 | 화면 | 음성 |
|---|---|---|
| **주행 중** | 작은 상태 카드 1개만 (도착 시 잔량, 다음 충전 추천 1곳). 터치 입력 없음 | 추천·경유지 추가 확인, 새 스탬프 알림 |
| **정차 중** | 전체 화면: 추천 비교, 주간 리포트, 도감, 이벤트, 포인트 | 없음 |
| **충전 중** | 적용 요금, 예상 절약액, 획득 예정 포인트·스탬프 | 충전 시작 시 1회 |

- **주행/정차 판별**: Vehicle SDK에 기어·속도 도메인이 없다. **Android Automotive 표준 주행 제한(UX restrictions)** 을 따르고 [제안], 보조로 위치 변화 속도를 쓴다. → [미정] Pleos 에뮬레이터에서 동작 확인 필요 (8절).

### 6-2. 화면 목록 [제안]

## 7. 기술 구조

### 7-1. 기반 [결정 — 스파이크 확인]
- Android (Kotlin), minSdk 28, Pleos Connect Emulator (API 34 Automotive)
- Pleos Connect SDK: **Vehicle 2.3.2**, **NaviHelper 3.0.5**, **FusedLocation**, **TextToSpeech**, **SpeechToText**
- 빌드: Gradle 8.14.3, AGP 8.13.0, Kotlin 2.2.20 (스파이크와 동일)

### 7-2. 모듈 [제안]

```
app/
├── vehicle/      VehicleRepository (인터페이스)
│                 ├─ PleosVehicleRepository  ← Vehicle SDK (SoC, 전비, 충전 상태, Odometer, VIN)
│                 └─ MockVehicleRepository   ← 시연·테스트용
├── navi/         NaviRepository (NaviHelper: 경로·거리·경유지 추가) + Mock
├── location/     FusedLocation (현재 위치, 지오펜스) + Mock
├── voice/        TTS·STT 래퍼
├── stations/     충전소·상태 데이터 (공공 API) + 요금표 (사업자별 회원가·로밍가·비회원가)
├── pricing/      추천 엔진 — 순수 Kotlin (도착 잔량, 실효 단가, 총비용, 순위)
├── rewards/      적립 규칙·원장(로컬 DB), 스탬프, 이벤트
├── drivestate/   주행/정차/충전 상태 판별
└── ui/           Compose 화면 (상태별)
```

- **pricing·rewards는 순수 Kotlin**으로 SDK와 분리해 단위 테스트한다.
- **SDK 호출은 Repository 한 겹 뒤에만** 둔다. SDK 시그니처는 컴파일러로 확인 (스파이크 교훈).
- 모든 Repository에 **Mock 구현**을 둔다 → Virtual Console 없이도 시연 시나리오 재생 가능.

### 7-3. 필요 권한
`pleos.car.permission.CAR_ENERGY`(EvBattery), `CAR_DRIVE`(Odometer), `CAR_INFO`(VIN), `NAVI_ROUTE`, `NAVI_ROUTE_SEARCH`(경유지), FusedLocation 권한, 마이크(STT). **차량 제어(`CONTROL_*`) 권한은 쓰지 않는다** — 별도 심사 대상.

### 7-4. 데이터 출처

| 데이터 | 출처 | MVP | 상태 |
|---|---|---|---|
| 배터리·전비·충전 상태·주행거리·VIN | Vehicle SDK | ✅ | 확인됨 (SoC·구독) / 일부 [미정] |
| 경로·거리·경유지 추가 | NaviHelper | ✅ | 경로 요청 확인됨 / 경유지 추가 [미정] |
| 충전소 위치·실시간 상태(고장·사용 중) | 공공데이터포털 한국환경공단 전기차 충전소 API [제안] | 목업 JSON | [미정] 제공 범위·갱신 주기 |
| 사업자별 요금 (회원가·로밍가·비회원가) | 사업자 공지·요금표 수집 → JSON [제안] | 주요 사업자 10곳 목업 | [미정] 공식 API 없음 |
| 차종별 배터리 용량·기준 전비 | 공개 제원 → JSON | ✅ | |
| 이벤트(레이드) 정보 | MVP는 앱 내 JSON, 이후 서버 | ✅ | |

- **서버는 MVP에서 두지 않는다** [제안]. 포인트 원장은 로컬 DB. 사업 구조(사업자 이벤트 등록, 제휴 정산)는 기획서에 설계로만 제시.
